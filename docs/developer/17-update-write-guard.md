# 17. bun 更新写规范与 internal_id 漂移修复

## 17.0 一句话

bun 的 UPDATE 必须显式声明写入列（`.Column` 白名单 / nil 模型 `.Set`），identity 列对 UPDATE 只读；违反此规范曾导致"改一次项目注册策略，`projects.internal_id` 就 +1"的数据面租户分裂事故（2026-09-08）。本文记录根因、规范、三道护栏与存量漂移修复 runbook。

## 17.1 事故复盘（2026-09-08）

**现象**：控制台修改一次项目注册策略，`projects.internal_id` 随之 +1。该列是数据面 `_tenant` 租户号与 roles_sig 验签 Tenant 的唯一来源，漂移 = 业务文档按租户分裂（读不到旧数据）+ `tw_roles()` 验签失配 fail-closed。

**根因链**（四个因素叠加，缺一不会发生）：

1. `model.Project.InternalID` 标了 `bun:"internal_id,autoincrement"`，bun 对 `autoincrement` 隐式置 `NullZero`（bun `schema/table.go`）；
2. pgdialect 启用 `DefaultPlaceholder` 特性：UPDATE 的 SET 列表中"零值 + nullzero"字段渲染为 `DEFAULT` 而非数值；
3. `mapProjectToModel` 不拷贝 `InternalID`（模型侧恒为零值），且 `UpdateProject` 是裸全模型覆盖写（struct + `WherePK()`，bun 渲染全部表列）；
4. 迁移 000001 定义 `internal_id BIGINT GENERATED BY DEFAULT AS IDENTITY`，其列 DEFAULT = `nextval`。

合成 SQL：`UPDATE "projects" SET "internal_id" = DEFAULT, ... WHERE id = ?` —— 每次执行烧一个序列号并把行改写成新租户号。**任何项目更新（改名/描述/注册策略）都触发**，不止注册策略。

**影响面**：事故窗口内该项目写入的文档 `_tenant` 为漂移后新值，与建表时烤进列 DEFAULT 的原值分裂；`ExecIdentity.Tenant`（roles_sig）以实时 `internal_id` 为准，随之失配。

## 17.2 bun 更新写规范（强约束）

全库 bun UPDATE 只允许两种形态：

```go
// 形态一：struct 供值 + 列白名单（实体字段级更新）
conn.NewUpdate().Model(m).
    Column("name", "entrypoint", "updated_at"). // 仅登记"创建后语义可变"的列
    WherePK().Exec(ctx)

// 形态二：nil 模型 + Set（列级/状态机更新，可加 CAS 条件）
conn.NewUpdate().Model((*model.X)(nil)).
    Set("status = ?", next).
    Where("... status = ?", expect).Exec(ctx)
```

- **禁止裸全模型覆盖 UPDATE**。bun 的规则是 SET 列集合 = struct 全字段（除非显式声明），"写哪些列"必须由代码声明，不能由 struct 恰好有什么决定。
- **identity / DB 生成列对 UPDATE 只读**：`model.Project.InternalID` 带 `skipupdate` 标签；outbox `seq` 是 `GENERATED ALWAYS`，任何 UPDATE 都不得触碰。
- **白名单登记纪律**：迁移新增列默认不进任何 UPDATE 白名单；功能上需要可变时显式登记。漏登记的后果是"改不动"（显式失败），而不是"静默清零"。
- **白名单速查**（当前登记）：`UpdateProject` → name/description/registration_policy/updated_at；`UpdateFunction` → name/entrypoint/timeout_seconds/spec/enabled/updated_at；`UpdateDeployment` → status/error/updated_at；`UpdateExecution` → status/response*/stdout*/stderr*/status_code/duration_ms/error/updated_at；asset def → name/decimals/max_quantity/expires_in/tradable/unique_per_owner/upgradeable/metadata/status/updated_at；subscription plan → name/amount/currency/interval/interval_days/grace_days/trial_days/benefits/provider_overrides/status/updated_at；subscription → user_id/plan_id/mode/provider/provider_sub_id/status/current_period_*/cancel_at_period_end/grace_until/billing_asset_code/benefits/updated_at。

### 指针列注意

指针列（如 `max_quantity`、`grace_until`）在 UPDATE 中为 nil 时同样渲染为 `DEFAULT`。当前所有指针列在迁移中无非平凡默认（`DEFAULT` ≡ `NULL`），语义等价；**将来新增"指针列 + 非平凡 DB 默认"的组合即重演同型事故**——指针列要么不进白名单（走 `.Set` 显式三态），要么保持列默认为空。

## 17.3 三道护栏

1. **AST 静态扫描**（`update_guard_test.go`）：扫描 `internal/infra` 全部非测试 Go 文件，任何 bun UPDATE 链必须含 `.Column`/`.Set`（含"变量承接后在同函数内 `.Set`"形态，apikey 先例），违者测试失败。豁免白名单 `updateGuardExceptions`（file:line，当前为空）。
2. **SQL 形状断言**（`project_repo_sqlshape_test.go`）：不依赖真实数据库——DSN 指向不可达端口，bun 在建连前先经 QueryHook 携带已渲染语句，断言 `UpdateProject` 的 SET 列集合精确等于白名单、恒不含 `internal_id`/`created_at`/`DEFAULT`；另以最小渲染锁死 `skipupdate` 标签语义（bun 升级行为变化立即红灯）。
3. **集成不变量**（`project_repo_internal_id_test.go`，需测试库）：真实 PG 上执行"改注册策略 → 重读"，断言 `internal_id` 不变——事故原样路径的回归锚点。

## 17.4 存量 internal_id 漂移修复 runbook

适用：事故窗口内发生过项目更新的环境。症状：项目文档读空/写 500、`tw_roles` fail-closed 日志、`_tenant` 分布分裂。

### 诊断

```sql
-- ① 控制面当前值（进程实时使用的租户号）
SELECT id, internal_id FROM public.projects WHERE id = '<project>';

-- ② 各业务表实际租户分布（逐库逐表）
SELECT _tenant, count(*) FROM tw_<project>_<database>.<collection> GROUP BY _tenant;

-- ③ 建表时烤进列 DEFAULT 的原值（各表可能不同——漂移后建的表烤的是漂移值）
SELECT pg_get_expr(ad.adbin, ad.adrelid) AS tenant_default
FROM pg_attribute a
JOIN pg_attrdef ad ON ad.adrelid = a.attrelid AND ad.adnum = a.attnum
WHERE a.attrelid = 'tw_<project>_<database>.<collection>'::regclass
  AND a.attname = '_tenant';
```

判定：② 中多数值（通常 = ③ 的 DEFAULT 表达式）即"真租户" `X`；`projects.internal_id` 当前值 ≠ `X` 即漂移。

### 修法 A：保数据（推荐，生产）

以 owner 身份（`tw_owner` 或建库 DSN）在维护窗口执行：

```sql
BEGIN;
-- 1. 归一业务行租户号（逐库逐表；只应命中漂移窗口内写入的少量行）
UPDATE tw_<project>_<database>.<collection> SET _tenant = X WHERE _tenant <> X;
-- 2. 控制面行改回真租户（BY DEFAULT identity 允许显式赋值）
UPDATE public.projects SET internal_id = X WHERE id = '<project>';
COMMIT;
```

要点：

- `X` 取**建表时烤入值**（③ 的 DEFAULT）可让多数存量行免回填；若某表是漂移后新建（DEFAULT 已烤成漂移值）而数据在旧值侧，则反之以数据多数侧为准，并接受该表全表回填。
- 系统静态表（users/sessions/…）无 `_tenant` 列，不在修复面内。
- 窗口内应暂停该项目写路径（否则进程缓存的漂移租户号会继续写入新分裂行）；改完无需重启——`internalIDCache` TTL（默认 30s）过期后自动切换到修复值。
- roles_sig 的 Tenant 是请求期实时派生，无存量状态需要处理。

### 修法 B：删项目重建（仅 dev / 数据可弃）

代码修复合入后直接删除项目重建（新 `internal_id` 一次性定型），数据从导入通道重放。

### 验证

修复后重跑诊断 ①②③：三者一致；项目文档 CRUD 正常；`tw_roles` 无 fail-closed 日志。可另跑 `internal/infra/documentdb` 的 `TestInternalIDCache_*` 套件确认缓存重验链路健康。
