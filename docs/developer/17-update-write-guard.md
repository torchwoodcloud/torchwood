# 17 bun 更新写规范与 internal_id 漂移修复

## 17.0 一句话

bun 的 UPDATE 必须显式声明写入列——struct 模型走 `.Column(白名单)`，nil 模型走 `.Set(...)`；identity / DB 生成列对 UPDATE 只读。护栏（静态扫描 + SQL 形状断言 + 集成不变量）在 `internal/infra/bun/bunrepo/`。背景：2026-09-08 曾因 `UpdateProject` 裸全模型覆盖写把 `projects.internal_id` 渲染成 `SET internal_id = DEFAULT`（= nextval），改一次注册策略就烧一个序列号并改写数据面租户号，导致文档按租户分裂 + `tw_roles()` 验签 fail-closed；本章是该事故对应的现行规范与存量修复 runbook。

## 17.1 机制：为什么禁止裸全模型 UPDATE

bun 对 struct 模型 UPDATE 的默认行为：**SET 列集合 = struct 全部表字段**，除非显式 `.Column(...)` 声明。字段值如何渲染由三个机制叠加决定：

1. `autoincrement` 标签隐式置 `NullZero`（bun `schema/table.go`：`autoincrement` ⇒ `NotNull + NullZero`）；
2. pgdialect 默认启用 `DefaultPlaceholder` 特性（`pgdialect.New()` 默认 feature 集的一员，本仓库未 `WithoutFeature` 关闭任何 feature）；
3. 遇 nil 指针或"NullZero + 零值"字段，bun 渲染字面量 `DEFAULT` 而非数值（bun `schema/field.go` `appendValue`，`defaultPlaceholder=true` 分支）。

"全模型覆盖 UPDATE + 恰好有 identity 列"即合成：

```sql
UPDATE "projects" SET "internal_id" = DEFAULT, ... WHERE id = ?
```

`projects.internal_id` 定义为 `BIGINT GENERATED BY DEFAULT AS IDENTITY`（`db/migrations/000001_control_plane.up.sql`），其列 DEFAULT = `nextval`：每次执行烧一个序列号，并把行改写成新租户号。该列是两条链路的唯一来源：

- **数据面 `_tenant`**：collection 物理表建表时把实时 `internal_id` 烤进 `_tenant BIGINT NOT NULL DEFAULT <n>`（`internal/infra/documentdb/postgres_collection_ddl.go`，建表路径取 `resolveInternalIDFresh` 强制回库值）；
- **roles_sig 验签 Tenant**：文档事务入口 `execIdentity` 每请求经 `resolveInternalID` 解析 `internal_id` 填入 `ExecIdentity.Tenant`，sig 消息覆盖 tenant（`internal/infra/documentdb/postgres_exec.go`）。

漂移的后果：`_tenant` 与 `internal_id` 分裂——存量文档读不到（RLS `tw_visible` 按租户过滤）、新写文档落新租户；roles_sig Tenant 随之失配，`tw_set_document_acl` 等校验 fail-closed。**任何项目更新（改名 / 描述 / 注册策略）都会触发，不止注册策略。**

当前代码是双层防御：

- **规范层**：`UpdateProject` 只写白名单列（`bunrepo/project_repo.go`），identity 列不进任何 UPDATE 白名单；
- **模型层**：`model.Project.InternalID` 带 `skipupdate` 标签（`internal/infra/bun/model/project.go`），即使误写全模型 UPDATE，该列也不进 SET。模型层是兜底而非豁免理由——`skipupdate` 语义本身由护栏 2 的最小渲染测试锁死。

### 指针列注意

指针列（如 `max_quantity`、`grace_until`）在 struct UPDATE 中为 nil 时同样渲染 `DEFAULT`。当前已登记白名单中的指针列在迁移里均无非平凡默认（`DEFAULT` ≡ `NULL`），语义等价；**将来新增"指针列 + 非平凡 DB 默认"的组合即重演同型事故**——指针列要么不进白名单（改走 `.Set` 显式三态），要么保持列默认为空。

## 17.2 bun 更新写规范（强约束）

全库 bun UPDATE 只允许两种形态：

```go
// 形态一：struct 供值 + 列白名单（实体字段级更新）
conn.NewUpdate().Model(m).
    Column("name", "description", "updated_at"). // 仅登记"创建后语义可变"的列
    WherePK().Exec(ctx)

// 形态二：nil 模型 + Set（列级 / 状态机更新，可加 CAS 条件）
conn.NewUpdate().Model((*model.X)(nil)).
    Set("status = ?", next).
    Where("... status = ?", expect).Exec(ctx)
```

形态二的高频变体是"白名单校验 + 动态 Set"：调用方传入列名 map，repo 对每个列名先过白名单（越界显式报错），再循环 `q = q.Set(col+" = ?", val)` 展开。api key（`apiKeyUpdateCols`）、user / group / bucket（domain 层 `Normalize*UpdateColumns`）等走此形态，范式见 `bunrepo/apikey_repo.go` 的 `UpdateAPIKey`。原生 SQL 更新（如 `SetProjectSetting` 的 `UPDATE projects SET settings = jsonb_set(...)`）写列显式在语句里，天然满足规范，也不经 bun 查询构造器。

规则：

- **禁止裸全模型覆盖 UPDATE**（struct + `WherePK()` 全列写）。"写哪些列"必须由代码声明，不能由 struct 恰好有什么决定。
- **identity / DB 生成列对 UPDATE 只读**：`projects.internal_id` 模型侧 `skipupdate`；outbox `seq` 是 `GENERATED ALWAYS AS IDENTITY`（迁移 000002），模型无 skipupdate 标签，但 INSERT 列白名单排除该列、UPDATE 不得触碰（DB 层 GENERATED ALWAYS 直接拒绝）。
- **白名单登记纪律**：迁移新增列默认不进任何 UPDATE 白名单；功能上需要可变时显式登记。漏登记的后果是"改不动"（显式失败），而不是"静默清零"。不可变列有意不登记同样是约定的一部分（如部署源快照五列 source_type / source_url / source_ref / source_dir / context_sha256，INSERT 期写全、之后不可变）。
- **零值归一**：白名单是全模型写，struct 零值会原样写入。带 CHECK 约束或语义默认的列在映射层归一（如 function 池策略列零值归一为平台默认，`bunrepo/function_repo.go` `mapFunctionToModel`）。

白名单速查（当前登记，与各仓储注释一一对应）：

| 更新方法 | 白名单列 |
| --- | --- |
| `UpdateProject` | name / description / registration_policy / updated_at |
| `UpdateFunction` | name / entrypoint / runtime / timeout_seconds / spec / enabled / declared_scopes / min_instances / max_instances / idle_ttl_seconds / max_requests_per_instance / concurrency / client_callable / client_anonymous_allowed / client_per_user_limit / client_limit_window / updated_at |
| `UpdateDeployment` | status / error / build_node / updated_at |
| `UpdateExecution` | status / response / response_truncated / stdout / stdout_truncated / stderr / stderr_truncated / status_code / duration_ms / error / updated_at |
| `UpdateTrigger` | token / config / enabled / next_run_at / updated_at |
| asset def `Update` | name / decimals / max_quantity / expires_in / tradable / unique_per_owner / upgradeable / metadata / status / updated_at |
| subscription plan | name / amount / currency / interval / interval_days / grace_days / trial_days / benefits / provider_overrides / status / updated_at |
| subscription | user_id / plan_id / mode / provider / provider_sub_id / status / current_period_start / current_period_end / cancel_at_period_end / grace_until / billing_asset_code / benefits / updated_at（status 带 expectStatus CAS） |
| leaderboard board | sort / tiebreak_order / tie_break / period_kind / period_tz / policy / value_min / value_max / client_submit / per_subject_limit / retention_periods / subject_kind / rewards / updated_at |

新增可变列的流程：迁移加列 → 在对应仓储的 `.Column(...)`（或域层 `Normalize*UpdateColumns`）显式登记 → 需要时补 SQL 形状断言。登记处注释写明不可变集合与登记理由，现有仓储注释即模板。

## 17.3 三道护栏

1. **AST 静态扫描**（`bunrepo/update_guard_test.go` `TestUpdateQueriesDeclareColumns`）：扫描 `internal/infra` 全部非测试 Go 文件（bun 生产使用面 = bunrepo 仓储 + events / realtime 的 outbox 状态更新；documentdb 等原生 SQL 不经 `NewUpdate`，天然不在扫描面）。任何 bun UPDATE 链必须含 `.Column` / `.Set`——链式直写与"变量承接后在同函数内 `.Set` / 再赋值"两种形态均被识别。豁免白名单 `updateGuardExceptions`（file:line 键）当前为空，注释明示"不要新增"。
2. **SQL 形状断言**（`bunrepo/project_repo_sqlshape_test.go`）：不依赖真实数据库——bun v1.2.18 无 DryRun API，测试用 QueryHook 技法（DSN 指向不可达端口 `127.0.0.1:1`，Exec 建连必失败，但 bun 在建连前回调 `BeforeQuery` 携带已渲染语句）。两个断言：
   - `TestUpdateProject_SQLShapeWhitelist`：`UpdateProject` 渲染 SQL 的 SET 列集合精确等于白名单（即便模型携带非零 `InternalID`），且恒不含 `internal_id` / `created_at` / `status` / `settings` / `DEFAULT`；
   - `TestProjectModel_SkipUpdateExcludesInternalID`：最小渲染锁死 `skipupdate` 标签语义。

   bun 升级改变渲染行为（尤其 `skipupdate` / `DefaultPlaceholder` 语义）时立即红灯。同一 render-only 技法已推广到 analytics 写/查询路径（`analytics_*_sqlshape_test.go`，见 `18-analytics.md`）。
3. **集成不变量**（`bunrepo/project_repo_internal_id_test.go` `TestUpdateProject_PreservesInternalID`，需测试库）：真实 PG 上执行"改注册策略 → 重读"，断言 `internal_id` 不变——事故原样路径的回归锚点。

## 17.4 存量 internal_id 漂移修复 runbook

适用：漂移已发生的环境（历史事故窗口、控制面被带外重置）。症状：项目文档读空 / 写 500、`tw_roles` fail-closed 日志、`_tenant` 分布分裂；现役进程还可能打出 WARN 日志 `project internal_id drift detected under running process`（`resolveInternalID` 回库核验发现漂移时产生，`documentdb/postgres_catalog.go`）。

### 诊断

```sql
-- ① 控制面当前值（进程实时使用的租户号）
SELECT id, internal_id FROM public.projects WHERE id = '<project>';

-- ② 各业务表实际租户分布（逐库逐表）
SELECT _tenant, count(*) FROM tw_<project>_<database>.<collection> GROUP BY _tenant;

-- ③ 建表时烤进列 DEFAULT 的原值（各表可能不同——漂移后建的表烤的是漂移值）
SELECT pg_get_expr(ad.adbin, ad.adrelid) AS tenant_default
FROM pg_attribute a
JOIN pg_attrdef ad ON ad.adrelid = a.attrelid AND ad.adnum = a.attnum
WHERE a.attrelid = 'tw_<project>_<database>.<collection>'::regclass
  AND a.attname = '_tenant';
```

判定：② 中多数值（通常 = ③ 的 DEFAULT 表达式）即"真租户" `X`；`projects.internal_id` 当前值 ≠ `X` 即漂移。

### 修法 A：保数据（推荐，生产）

以 owner 身份在维护窗口执行：

```sql
BEGIN;
-- 1. 归一业务行租户号（逐库逐表；只应命中漂移窗口内写入的少量行）
UPDATE tw_<project>_<database>.<collection> SET _tenant = X WHERE _tenant <> X;
-- 2. 控制面行改回真租户（BY DEFAULT identity 允许显式赋值）
UPDATE public.projects SET internal_id = X WHERE id = '<project>';
COMMIT;
```

要点：

- `X` 取**建表时烤入值**（③ 的 DEFAULT）可让多数存量行免回填；若某表是漂移后新建（DEFAULT 已烤成漂移值）而数据在旧值侧，则反之以数据多数侧为准，并接受该表全表回填。
- 系统静态表（users / sessions / …）无 `_tenant` 列（`internal/infra/projectschema/migrations/000008_system_tables.up.sql`），不在修复面内。
- 窗口内应暂停该项目写路径（否则进程缓存的漂移租户号会继续写入新分裂行）。改完无需重启：`resolveInternalID` 的进程内缓存带 30s 回库核验间隔（`documentdb/postgres.go` `defaultInternalIDReverify`），过期后首次访问即回库比对，发现值变化自动切换缓存并打 WARN。
- roles_sig 的 Tenant 是请求期实时派生（`execIdentity` → `resolveInternalID`），无存量状态需要处理。

### 修法 B：删项目重建（仅 dev / 数据可弃）

直接删除项目重建（新 `internal_id` 一次性定型），数据从导入通道重放。同 ID 删建路径由 `InternalIDCacheInvalidator` 主动失效进程内缓存（`documentdb/postgres_catalog.go`），不会以陈旧租户号污染新实例。

### 验证

修复后重跑诊断 ①②③：三者一致；项目文档 CRUD 正常；`tw_roles` 无 fail-closed 日志。可另跑 `internal/infra/documentdb` 的 `TestInternalIDCache_*` 三例（`InvalidationOnRecreate` / `TTLReverify` / `StaleEntryOnMissingRow`）确认缓存重验链路健康。
